## 1. Goal

Require every contributor to accept a Contributor License Agreement (CLA) before their PR can be merged. The CLA grants
the project (BBV CH / Swiss AI-Hub maintainers) the rights needed to relicense the codebase in the future.

The implementation has three pieces:

1. A `CONTRIBUTOR_AGREEMENT.md` at the repo root (text adapted from Salesforce's Individual CLA, itself based on the
   widely-used Apache ICLA template).
2. A GitHub Actions workflow (`.github/workflows/cla.yml`) using the
   [contributor-assistant/github-action](https://github.com/contributor-assistant/github-action) ("cla-assistant lite")
   that posts a comment on every PR from a new contributor, captures their signature as a PR comment, and stores
   signatures in a separate gist or signatures repo.
3. Documentation updates so contributors discover the requirement (CONTRIBUTING.md and a PR template note).

## 3. Architecture alignment

Pure repo-level governance. No package code is touched. The workflow runs on `pull_request` (NOT `pull_request_target` —
that trigger gives a workflow write access to the base repo while executing on fork-supplied refs and is a documented
privilege-escalation risk) and `issue_comment` (so the bot can record a signature when a contributor comments the
agreement phrase). It is independent of, and does not interact with, the existing CI workflows (`lint-pr`,
`semantic-pr`, `build-*`).

**Known trade-off from using `pull_request` instead of `pull_request_target`:** for PRs opened from forks, the
workflow's `GITHUB_TOKEN` has no write permission on the base repo's PR, so the bot **cannot post the "please sign"
comment** on those PRs. Same-repo PRs (the common case for maintainers) work fully. Fork contributors will see a failing
`CLA Signature Check` status check and must learn the sign-off phrase from `CONTRIBUTING.md` and
`.github/pull_request_template.md`, both of which surface it prominently. The `issue_comment` trigger always runs in
base-repo context, so once a fork contributor knows the phrase and posts it, the bot still records the signature
normally.

### 4.2 NEW — `.github/workflows/cla.yml`

```yaml
---
name: CLA Assistant
on:
  issue_comment:
    types: [created]
  pull_request:
    types: [opened, closed, synchronize]
permissions:
  actions: write
  contents: read
  pull-requests: write
  statuses: write
jobs:
  cla:
    name: CLA Signature Check
    runs-on: ubuntu-24.04-arm
    if: >
      (github.event.comment.body == 'I have read the CONTRIBUTOR_AGREEMENT and I hereby sign the CLA') ||
      github.event_name == 'pull_request'
    timeout-minutes: 5
    steps:
      - name: CLA Assistant
        uses: contributor-assistant/github-action@v2.6.1
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          PERSONAL_ACCESS_TOKEN: ${{ secrets.CLA_ASSISTANT_PAT }}
        with:
          path-to-signatures: signatures/v1/cla.json
          path-to-document: https://github.com/bbvch-ai/aihub-core/blob/main/CONTRIBUTOR_AGREEMENT.md
          branch: main
          allowlist: dependabot[bot],claude[bot],bbvch-ai-bot
          remote-organization-name: bbvch-ai
          remote-repository-name: cla-signatures
          custom-pr-sign-comment: I have read the CONTRIBUTOR_AGREEMENT and I hereby sign the CLA
          custom-notsigned-prcomment: >
            Thank you for your contribution! Before we can merge, please read our
            [CONTRIBUTOR_AGREEMENT](https://github.com/bbvch-ai/aihub-core/blob/main/CONTRIBUTOR_AGREEMENT.md)
            and sign by commenting the phrase below on this PR.
          custom-allsigned-prcomment: All contributors have signed the CLA ✅
          lock-pullrequest-aftermerge: false
```

Design notes:

- Trigger is plain `pull_request`, **not** `pull_request_target`. `pull_request_target` would let the workflow comment
  on fork PRs but would also execute on the base repo with secrets and write access — a documented privilege-escalation
  surface. We accept reduced fork-PR ergonomics in exchange for that safety.
- For fork PRs, the bot cannot post the initial sign-off prompt. The failing `CLA Signature Check` status is the
  contributor's only in-PR signal; they discover the sign-off phrase from `CONTRIBUTING.md` and
  `.github/pull_request_template.md`. The `issue_comment` job still records signatures normally once the phrase is
  posted (issue_comment events always run in the base-repo context regardless of fork origin).
- Allowlist excludes bot accounts (`dependabot[bot]`, `claude[bot]`) — their PRs are merged by maintainers under the
  maintainers' CLA.
- Signatures stored in a **separate private repo `bbvch-ai/cla-signatures`** (must be bootstrapped — see §6), not in
  this repo, so revoking access doesn't lose history.
- Pin to a specific minor (`@v2.6.1`) rather than `@v2` for supply-chain safety. Dependabot will offer upgrades.

### 4.3 EDIT — `CONTRIBUTING.md`

Add a new section between the existing "License" section (currently the last section) and the closing line. The license
clause stays — it tells contributors *what* licensing scope they grant; the new CLA section tells them *how* they record
that grant.

New section text:

```markdown
## ✍️ Contributor License Agreement (CLA)

To accept your contribution we need you to sign our Contributor License Agreement. This is a one-time step per
GitHub account.

1. Read [CONTRIBUTOR_AGREEMENT.md](./CONTRIBUTOR_AGREEMENT.md).
2. When you open a Pull Request, the CLA Assistant bot will comment with sign-off instructions if you haven't
   signed yet.
3. Add a PR comment with the exact phrase the bot asks for. The bot will record your signature in the
   `bbvch-ai/cla-signatures` repository.
4. Once signed, the CLA check turns green and your PR is eligible for merge.

If you contribute on behalf of your employer, please confirm that you have your employer's permission to
submit the work and to grant the licenses described in the agreement.
```

## 6. Manual deployment steps (out of code scope — for maintainers after merge)

These steps cannot be done from the repo and must be flagged in the PR description:

1. **Create a separate signatures repository** at `bbvch-ai/cla-signatures` (private, empty, default branch `main`) —
   used by the bot to persist `signatures/v1/cla.json`.
2. **Create a PAT** with `repo` scope and write access to `bbvch-ai/cla-signatures`. Store as `CLA_ASSISTANT_PAT` repo
   secret on `bbvch-ai/aihub-core`.
3. **Add `CLA Signature Check` to required status checks** on `main` branch protection (Settings → Branches → Branch
   protection rules → main → Require status checks to pass). Without this, the workflow comments but doesn't actually
   block merges.
4. **Communicate the change** to existing contributors (Discord + a discussion post). Existing maintainers should sign
   once so their future PRs are pre-cleared.

## 7. Out of scope

- **Legal review by Adrian.** The CONTRIBUTOR_AGREEMENT text is a *draft*. Adrian must approve before the file's "DRAFT"

- **Backfilling signatures from past contributors.** The bot only enforces from the moment the workflow is enabled.

- **Corporate CLA (CCLA).** Deferred per the user's decision (Individual CLA only for now). Can be added later as a

## 9. Test plan

This change is YAML + Markdown only, so there are no unit tests to write. Verification is:

1. **Static**: `yamlfix` + `mdformat` hooks pass (run automatically by the PostToolUse hooks).
2. **Manual smoke after merge** (in a follow-up PR by a fresh contributor or test account):
   - Open a PR from a non-allowlisted account → bot comments with the sign-off request.
   - Comment the sign-off phrase → bot updates the comment, status check turns green.
   - Open a second PR from the same account → status check is green immediately (no second prompt).
   - Confirm `signatures/v1/cla.json` in `bbvch-ai/cla-signatures` lists the contributor.

Smoke is best done on a throwaway test PR after deployment steps §6.1–§6.3 are complete.
